# Reproducible benchmark scenarios

Record commit, dirty status, Go version, OS/architecture, CPU model/count, Gin mode, dataset, concurrency and logger destination with every result. Paired BenchmarkComparison GET and database cases compare the same responses/rows; logging is disabled for core timing. `benchcheck` requires at least three balanced samples and checks existing same-run overhead budgets (HTTP 5x Gin, database 2x GORM). These are initial overhead ceilings, not a 10% historical regression guarantee.

`go run ./internal/tooling/loadcheck -scenario=post -concurrency=16 -requests=10000 -duration=5s` runs a loopback HTTP server and records throughput, p50/p95/p99, errors, deadline cancellations, heap and goroutine snapshots. Other scenarios are get, params and error (expected 404 is a successful workload response). `-telemetry` measures request logger/trace/metric CPU/allocation effects with log output discarded; disk/network log delivery is excluded. CPU/heap profiles use -cpu and -heap paths. At most 100000 latency samples, 256 clients and five minutes are accepted.

Deadline cancellations are reported separately; non-cancellation failures fail the harness. Short CI runs are bounded burst/saturation probes, not long-duration soak certification. Run repeated five-minute probes plus process/runtime monitoring on controlled deployment hardware to investigate retained memory and tail latency. Compare equivalent workloads on the same machine; a >10% sustained change deserves investigation only after measurement variation is established. Shared-host CI does not support a universal absolute latency SLO.

The performance workflow records environment, five paired samples, all API workloads, optional telemetry profiles and a 128-client burst as retained artifacts. The gRPC/TLS and real-DB paths have separate integration tests; loopback API latency must not be presented as PostgreSQL/RPC latency. Controlled gRPC/database latency profiles and a longer soak remain explicit release-review evidence until measured.
